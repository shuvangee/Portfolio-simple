A router that picks the cheapest AI model that can still get the answer right

01 / The problem

How much model does a request need?

Sending every request to a larger model can add cost and latency without improving every answer. Always choosing a smaller model can miss the tasks that need more capability. I wanted to measure whether routing could preserve answer quality while reducing usage of the larger model.

My work covered the full system: benchmark design, automated grading, real-model evaluation, the routing API and interface, and a learned alternative evaluated against simpler baselines.

02 / The system

Two strategies, one request pipeline.

  1. Next.js interface
  2. FastAPI + request analysis
  3. Routing strategy
  4. Groq model + response trace

D2: the preferred rule

Send summarization to gpt-oss-120b and everything else to gpt-oss-20b. The policy is small enough to inspect directly and routes just 6 of the 92 evaluated tasks to the larger model.

Learned-v2: the alternative

A shallow decision tree predicts whether to use 120B from information available before execution: category, difficulty, structured-output requirements, and estimated input tokens. It is trained offline and remains selectable for comparison.

03 / Evaluation design

Measure the answer, not just the routing label.

I built 104 tasks across eight categories: extraction, classification, summarization, math, reasoning, coding, debugging, and structured output. Automated grading covered 92 tasks using checks including exact answers, label matching, JSON validation, sandboxed code execution, and required facts. The other 12 stayed manual-only and were excluded from the reported accuracy.

Both models had recorded outcomes for the same 92 tasks. Leave-one-out cross-validation evaluated routing choices on held-out tasks; each choice was scored using the selected model’s recorded correctness, token cost, and latency. This measures the outcome of the whole system rather than whether a classifier reproduced an escalation label.

A broader category rule initially reached 91.3% accuracy on the data used to derive it, but fell to 88.0% under cross-validation. The narrower D2 rule retained 90.2%. That difference made evaluation design central to choosing the default.

The oracle assumes prior knowledge of which answer is correct; it is a theoretical upper bound, never a deployable strategy.

D2 matched the larger model’s 83 correct answers while using it only 6.5% of the time. The learned router used it 23.9% of the time and produced 81 correct answers. On this benchmark, the additional complexity bought neither higher accuracy nor lower cost.

05 / What I learned

A working learned router can still be the wrong default.

Only eight tasks had different correctness outcomes between the models, and only five favored escalating to 120B. That sparse signal is a plausible explanation for the learned router’s result; it is not evidence that learned routing fails in general.

I also compared logistic regression, which scored 89.1% while using 120B for 41.3% of tasks. The decision tree’s one-task accuracy deficit was treated as a practical tie, with lower nominal cost breaking it. That was an engineering selection rule, not a statistical demonstration that the models were equivalent.

The final decision was to keep both strategies available and make D2 the application’s default. Reporting the negative result made the project more useful: the next iteration has a concrete baseline to beat.

06 / Scope and next steps

What these results can support.

This is a small, project-designed benchmark with two candidate models and 12 tasks outside automated scoring. Matching accuracy here does not guarantee the same result on new traffic, and the tagline describes the routing objective rather than a guarantee that every answer will be correct.

Cross-validation informed strategy selection on this dataset. A separate, untouched evaluation set would provide stronger evidence of generalization. Free-tier costs and recorded call latency also do not establish paid-deployment economics or production performance.

The repository documents a runnable application and production build instructions, but does not provide a live deployment URL. Without a provider key, demo mode illustrates routing and traces using a mock fallback; those responses are separate from the real-model benchmark evidence.

My next steps would be to expand the tasks where the models disagree, evaluate on fresh data, and test whether a third model helps on tasks both current models miss before adding more routing complexity.
